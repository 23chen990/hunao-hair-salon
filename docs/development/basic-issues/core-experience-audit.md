# 基础体验审计：地图以外问题

> 2026-09-30 之后的变化：客流节奏、口碑可见和第二洗发区已实施，下文“客流满载”“声望关闭”“4 号洗发位不可用”是审计当时的状态。当前进度见 [基础问题清单](README.md)。

审计范围：手机横屏正式玩法的操作理解、服务流程、营业节奏、内容重复、成长、关闭系统、存档与隔天衔接。  
证据优先使用 `unity-hair-salon/Builds/CompetitorBalanceFullDay/run1/` 两日真实触控记录；`states.json` 共 1,437 帧、95 个操作，视口 844×390。状态文件没有逐帧时间戳，下面涉及“时长”的统计统一写成“帧采样时段”，不把帧数擅自换算成秒。

## P1：明显影响好玩

### 1. 产能与客流严重失衡，玩家大部分营业时间都在处理等待，而不是做服务决策

- **玩家会遇到什么**：即使固定路线能完成目标，店里仍长期堆满顾客；玩家不断跑向队列，很多顾客耐心降到 0 或在打烊时仍未处理。达标更像“脚本跑够订单”，而不是稳定掌控店面。
- **证据**：
  - `run1/report.json`：两日完成 `5/3`、`6/4`，但 `maxWaiting=4`；第 1 天结算截图 `run1/05-result.png` 显示“流失顾客 1、未完成服务 2、打烊未接待 2”。
  - Python 统计 `run1/states.json`：等待人数非零 1,381/1,437 帧（96.1%），未接待等待顾客非零 1,329/1,437 帧（92.5%），关注需求非零 1,381/1,437 帧（96.1%）；13 位顾客中至少 2 位曾出现耐心 `0.0`。各顾客处于 `Waiting` 的采样帧数为 `32–727`，中位数 271。
  - 代码：`SalonMobileDayConfig.cs:148-178` 固定等待容量 4、并发 6、刷新间隔 5.5–8.5 秒、后段强度最高 1.45；`BusinessDaySystem.cs:225-247` 在等待过载时才放慢刷新，容量达到 4 才停止刷新。
- **根因**：当前“目标单数”与“允许生成的顾客压力”是两套指标；超过目标后仍会继续营业和进客，而可同时处理的主动服务上下文有限。后台吹发虽然释放玩家，但不能消化洗发、剪发和接待的所有瓶颈。
- **建议修法方向**：先用真人首局数据重新校准“完成目标所需产能”和“目标外顾客数量”；明确达标后的继续营业是奖励性自由营业还是仍持续制造惩罚。让客流压力形成可读的优先级选择，而不是长期满队。优先验证单人、非固定路线玩家的完成率、走单数、满意度曲线和下一局意愿。
- **是否需要产品负责人批准**：需要。会改变营业节奏、客流规则或目标体验。
- **规模**：中。

### 2. 满意度和声望不是同一条可玩的成长反馈，玩家做得好却无法形成长期经营回报

- **玩家会遇到什么**：营业中能看到满意度，日结也显示满意度；但“服务好 → 店铺声望 → 明天客流/收益”的经营反馈并未真正形成。玩家很难理解自己为什么要追求更好服务，而不是只凑够目标单。
- **证据**：
  - `SalonGameModel.cs:255-260` 明确 `ReputationSystemEnabled = false`。
  - 主任务复核更正：这个常量只被一条“声望不显示”的测试引用，不控制结算。`SalonDemo.cs:966` 每天打烊都会调用 `FinalizeDayReputation()`，`SalonDemo.cs:1201-1202` 把当前星级传给客流导演（最多 ±10%），`SalonDemo.Mobile.cs:792` 会存档星级。所以问题是玩家看不见、幅度太小，而不是没有接线。
  - `docs/development/competitor-balance/REPORT.md:58-68` 明确扩展玩法中的口碑—客流循环、宣传投入仍是待批准提案；当前限制还写明固定路线不能证明好玩。
  - `run1/report.json` 只证明两日满意度为 88、87，不能证明声望带来了下一日客流变化；`states.json` 的 `target` 仍为第 1 天 3、第 2 天 4。
- **根因**：声望模型、声望存档字段和日结展示虽然存在，但核心开关关闭，营销枚举也没有形成可购买、可生效的经营选择。即时满意度与长期声望没有向玩家解释两者关系。
- **建议修法方向**：先确定声望是否属于当前版本的核心循环；若保留，接通最小闭环：可观察的日结变化、次日客流影响、失败后的恢复方式，以及不会造成死亡螺旋的保护。若暂不做，就从当前体验承诺中移除相关暗示，避免显示一套不产生玩法后果的经营指标。
- **是否需要产品负责人批准**：需要。涉及长期经营玩法、客流和反馈方向。
- **规模**：大。

### 3. 扩建目前有即时数值收益，但成长路线短，且“闭店经营”与已确认的空间施工方向不一致

- **玩家会遇到什么**：玩家完成首个扩建后主要得到一个额外理发工位；闭店时进入弹出式面板购买自动吹风升级。继续营业几天后，店铺动线、决策和经营方式没有明显新变化，成长容易变成“攒钱买下一项”。
- **证据**：
  - `run1/06-management.png`、`run1/12-day2-management.png`：闭店经营是面板，当前主要购买自动吹风支架/升级；`run1/13-day2-management-reload.png` 证明已购状态可恢复，但没有显示新的营业玩法层。
  - `SalonDemo.cs:780-807` 直接构建“闭店经营”弹窗，列出自动吹风、基础吹发和升级收益；`SalonDemo.Mobile.cs:590-640` 的正式空间施工只覆盖第二理发工位。
  - `docs/decisions/0003-hair-salon-hybrid-casual-loop.md:70-127` 已确认的方向是场景内施工圈、现场组装，并要求扩建改变路线、容量或服务效率；同时也明确当前通用连续施工点尚未实现。
- **根因**：当前已实现扩建、闭店购买和 0003 设计目标是三种不同形态；订单量和工位能力增加后，没有相应的新阻碍、新路线或新决策承接。
- **建议修法方向**：先确定当前版本的成长终点和每次扩建要改变的具体决策，再统一购买形态。优先让已批准的施工圈与实际能力、路线、存档和下一阶段压力成闭环；不要只增加商品数量。
- **是否需要产品负责人批准**：需要。涉及扩建形态、后期玩法和场景交互。
- **规模**：大。

### 4. 存档能保留经营结果，但不能恢复中途服务现场，刷新/隔天衔接会打断玩家正在处理的任务

- **玩家会遇到什么**：刷新或重新进入后能保留余额、天数和已购扩建，但不能回到顾客位置、洗发泡沫、吹发计时或当前服务动作。玩家在一局中途离开，回来需要重新理解现场，甚至丢失正在倒计时的服务节奏。
- **证据**：
  - `docs/development/first-session-repair/REPORT.md:60-63` 明确写出：刷新恢复经营进度/准备阶段，不承诺恢复顾客位置和正在进行的服务现场。
  - `SalonProgressSave.cs:5-17` 明确存档只保存 durable business progress，实时顾客、计时器和场景对象由玩法层恢复；字段见 `SalonProgressSave.cs:20-37`，只有天数、余额、扩建、满意度、声望和完成日历史。
  - `run1/13-day2-management-reload.png` 可证明结果和购买状态能恢复，但不能证明服务现场恢复。
- **根因**：存档边界按“营业结果”设计，没有定义中途退出时是安全暂停、回滚到开店，还是保存服务现场；三者对玩家预期不同。
- **建议修法方向**：明确移动端中途退出策略。短期至少在退出/刷新前给出明确安全边界，避免让玩家以为服务状态会继续；长期若要求可随时恢复，再设计顾客、工位、服务计时和营业倒计时的可序列化快照。
- **是否需要产品负责人批准**：需要。涉及退出惩罚和存档体验。
- **规模**：中（明确回滚/安全边界）或大（完整恢复现场）。

### 5. “烫发”在世界里出现，但正式手机流程永远把它锁死，形成半成品系统和错误期待

- **玩家会遇到什么**：玩家能看到烫发区和相关顾客/订单代码痕迹，却没有正常可获得、可使用的烫发工位；这会让人以为自己漏了某个解锁条件，或误判订单无法完成。
- **证据**：
  - `SalonDemo.cs:550-575` 创建烫发区和工位锚点，但 `SalonDemo.cs:240-245` 手机开局调用 `ConfigureWorkstationAvailability(..., false, false)`，第二、第三个可扩展能力均关闭；`SalonMobileDayConfig.cs:176-180` 当前订单池只有 O001–O005。
  - 主任务复核更正：`SalonDemo.cs:797-799` 的“染发设备/烫发设备 LOCKED”文案只在非手机模式出现；手机闭店面板显示的是“基础吹发”和“升级收益”，所以手机玩家不会看到这行锁定文字。
  - `run1/04-pressure.png` 的订单气泡主要展示剪发、洗发、吹发链，没有任何可完成的烫发路径。
- **根因**：通用模型和旧桌面/未来服务链保留了烫发数据，但手机正式内容没有解锁条件、订单来源或完成路径。
- **建议修法方向**：当前版本若不包含烫发，应从正式可见路径中明确降级为开发占位；若要保留，则必须同时定义解锁条件、订单池、用品、服务反馈、失败规则和存档，不要只打开一个工位。
- **是否需要产品负责人批准**：需要。涉及服务内容和解锁路线。
- **规模**：中。

## P2：打磨问题

### 6. 后台服务有规则，但“什么时候必须回来”仍主要靠静态文字，关键状态缺少强反馈

- **玩家会遇到什么**：泡沫完成后可以离开、吹发可以后台运行，但玩家需要持续扫视顾客气泡、顶部任务条、队列卡和右侧按钮才能知道哪个服务已经可以收尾。压力截图中多个顾客卡、顶部任务和当前动作同时出现，信息优先级不明显。
- **证据**：
  - `run1/03-background.png`、`run1/04-pressure.png`：画面同时出现多张顾客卡、顶部目标/库存、顾客气泡、底部进度和右侧操作按钮；当前动作是“吹发运行中/洗发中”，但其他顾客的待处理状态仍需逐项读取。
  - `run1/states.json`：`readyToRinse` 非零 180/1,437 帧（12.5%），`autoBlowReady` 非零 544/1,437 帧（37.9%）；最长单一提示包括“靠近顾客”40 帧、“吹发运行中”40 帧、“泡沫中”13 帧。“等待空闲工位”共 9 帧。
  - `docs/development/competitor-balance/REPORT.md:69-70` 已记录泡沫迟到目前只靠进度条变色，没有闪烁或警报音。
- **根因**：服务规则允许交错，但状态反馈仍以多个并列信息源为主，缺少“最该先处理的一个任务”和临界状态变化。
- **建议修法方向**：不做视觉重设计的前提下，增加状态变化级反馈：泡沫/吹发进入可收尾、即将超时、事故时使用短促声音或轻量动效；让当前最高优先级任务在现有提示区域中稳定置顶。
- **是否需要产品负责人批准**：通常不需要，若新增音效/动效仍保持当前 UI 方向；若改变信息层级或新增 HUD 区域，需要批准。
- **规模**：小到中。

### 7. 订单组合和工具节奏变化有限，连续营业容易感觉只是同一套洗剪吹重复

- **玩家会遇到什么**：完成几单后主要仍是在接待、安排、洗发、剪发、吹发之间重复跑动；订单变化虽有 O001–O005，但没有足够强的新规则或新障碍来改变优先级。
- **证据**：
  - `SalonMobileDayConfig.cs:176-180` 订单权重固定只有 O001–O005；`SalonMobileDayConfig.cs:208-231` 各日只是从相同五个订单池按进度重新抽取。
  - `SalonMobileDayConfig.cs:232-251` 工具变化主要是首单剪刀、后续剪刀+打薄剪，偶尔推子；没有新的服务机关承接第 2 天以后。
  - `run1/report.json` 两日完成 11 单，但 `businessDaysRequested=2` 的报告没有记录新的服务系统或机关被解锁。
- **根因**：日数、目标数和客流强度在增长，内容规则仍主要复用同一组订单和工序。
- **建议修法方向**：在基础动线稳定后，为每个阶段批准一个可识别的新约束或新机会，要求它改变服务顺序/路线/风险，而不是只换订单图标；每项新增内容都应有失败后果和补救方式。
- **是否需要产品负责人批准**：需要。涉及新玩法和内容扩展。
- **规模**：大。

### 8. 真实触控审计能证明流程可执行，但还不能证明虚拟摇杆和按住/松手手感可靠

- **玩家会遇到什么**：固定脚本可以完成两日营业，但陌生玩家可能遇到摇杆死区、移动方向不符合预期、按住剪发误松手或多指操作冲突。
- **证据**：
  - `run1/report.json` 只记录 Chromium real touch events、`haircutGestureChecks=true`、`errors=[]`；`run1/states.json` 统计中摇杆有输入 1,390/1,437 帧（96.7%），空闲 43/1,437 帧（3.0%），只能说明脚本大部分时间在跑动，不能评价触感。
  - `docs/development/competitor-balance/REPORT.md:69-70` 明确尚未在实体手机验收；`docs/development/first-session-repair/REPORT.md:57-63` 也说明当前仅为 Chromium 横屏模拟。
- **根因**：现有自动化记录动作结果和状态，不记录触控延迟、误触、手指滑出按钮、设备帧率或玩家主观困惑。
- **建议修法方向**：安排至少一轮实体手机和陌生玩家测试，记录摇杆到角色响应延迟、有效移动比例、误触/漏触、剪发松手失败率，以及第一次完成一单所需时间。
- **是否需要产品负责人批准**：不需要做审计，但若据此调整操作容错、按钮行为或交互方向，需要批准。
- **规模**：中。

## 待验证（不计入上述已确认问题）

1. **实体手机性能与触控手感**：当前只有 844×390 Chromium 真实触控，没有 iOS/Android 实机证据；不能据此判断发热、掉帧、摇杆漂移或触控延迟。
2. **陌生玩家首局完成率与放弃点**：固定脚本两日达标不代表新玩家能理解优先级；需要观察第一次看到泡沫/吹发后台任务、第一次错误工位、第一次缺货和第一次闭店后的实际困惑。
3. **玩家是否觉得扩建“明显变好玩”**：现有报告证明第二理发工位和补货架能保存、能改变可用工位/路线，但没有对比扩建前后的单位时间完成数、跑动距离和主观动力。
4. **摄像机、人物与 HUD 的遮挡是否仍影响操作**：历史报告记录过边角遮挡和双人底部按钮覆盖，当前任务要求暂不审计地图/UI 重设计；若遮挡使目标不可读，应另做当前构建的画面复核。
5. **跨天耐心加速是否合适**：代码在 `SalonMobileDayConfig.cs:128-132` 让第 2 天起耐心下降从 0.85 提到 1.0，但现有两日固定路线不足以判断这是合理压力还是突然变难。
6. **关闭/半成品系统的取舍**：营销枚举、声望开关、烫发工位和未来机关都已在代码或文档中出现，但是否应在当前版本隐藏、补完或延后，需要产品负责人明确范围。

## 建议修复顺序（前 5 项）

1. **先校准单人客流与产能**：围绕等待长期满 4、耐心归零和打烊未处理，确定目标单数、刷新、过载保护和达标后继续营业的关系。
2. **补齐“即时满意度—声望—次日经营”的产品闭环，或明确移除未接通的经营暗示**：避免玩家只为凑目标单。
3. **统一扩建/闭店购买方向**：明确施工圈、面板购买和自动化升级的关系，让每次扩建确实改变路线、容量或服务决策，并能跨天保存。
4. **处理烫发及其他半成品入口**：在正式手机版本中明确隐藏/降级，或补齐完整解锁、订单、服务和存档链，避免玩家误以为漏条件。
5. **强化后台服务和堵点的状态反馈**：在不做 UI 重设计的前提下，加入可收尾/临界超时的轻量变化和优先级提示；随后用陌生玩家与实体手机验证操作手感。
