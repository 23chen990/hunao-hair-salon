# 店铺空间、地图与扩建事实审计

审计范围：只核实现有手机正式 Demo、批准文档和可访问的竞品资料；没有修改代码、场景或配置，也没有运行 Unity、构建或浏览器检查。

## 先说结论

“店铺地图定死且很小”只说对了一半：当前手机入口确实只有一个固定房间，开局用碰撞边界限制为 A 区；理发扩建后只是把同一房间的可走宽度从 15.1 增到 20.7，当前没有真正的新房间、等待区、后场通道或门口外摆。扩建存在，但更像“在固定房间里开一件家具/打开一段地板”，还不是《Monkey Mart》式的连续空间成长。

## 1. 当前空间的量化事实

### 1.1 可走面积与增长

- 开局可走边界是 `Rect(-10.35, -5.15, 15.1, 12.45)`，矩形面积约 **188.0 平方世界单位**。扩建后的边界是 `Rect(-10.35, -5.15, 20.7, 12.45)`，面积约 **257.7 平方世界单位**。来源：`unity-hair-salon/Assets/Scripts/SalonDemo.Mobile.cs:84-85`。
- 因而理发扩建增加约 **69.7 平方世界单位**，相对开局增加 **37.1%**，扩建后是开局的 **1.37 倍**，不是两倍地图，也不是新增一张地图。来源同上；运行时按扩建状态选择边界：`SalonDemo.Mobile.cs:770-778`。
- 开局还有一条 `Rect(4.75, -2.8, 0.5, 8.9)` 的临时障碍，把尚未扩建的右侧区域隔开；扩建后这条障碍不再加入移动碰撞。来源：`SalonDemo.Mobile.cs:770-778`。这意味着“扩建”同时是打开同房间右侧通行，不是加载新房间。
- 现有证据截图能看到完整店铺外轮廓、后墙货架、洗发区、等待区和收银区都在同一室内壳体中；开局截图：`artifacts/p107/mobile/01-opening.png`。该截图是视觉佐证，不等同于精确地图测量。

### 1.2 镜头一屏覆盖比例

- 手机验收视口基准是 **844×390**：`PROJECT_CONTEXT.md:80-81`；当前移动跟随相机正交尺寸为 **6**：`SalonDemo.Mobile.cs:990-998`。因此不考虑透视和 UI 安全边距时，垂直世界视野约 **12** 个单位，横向名义视野约 `12 × 844/390 = 26.0` 个单位。
- 房间高度是 12.45，单看世界轴高度，一屏名义覆盖约 **96.4%** 的房间高度；横向名义视野大于开局宽度 15.1 和扩建宽度 20.7。不能把 `26.0 × 12` 直接当成真实可见店铺面积，因为正式相机有俯视旋转，代码按相机 `right/up` 投影、墙角和角色安全边距重新取景：`SalonDemo.Mobile.cs:1001-1053`。
- 产品层可准确表述为：**镜头不是只能看一个小角落，而是大部分时间能覆盖房间的大范围；问题在于房间本身横向内容有限，扩建后也没有产生第二个可独立探索的空间。** “一屏覆盖店铺面积百分比”没有现成运行遥测，不能伪造一个精确面积百分比。
- 初版确实出现过目标工位和角色同时在屏幕外的问题；坐标和 844×390 复现记录见 `docs/development/first-session-repair/camera.md:5-9`。修复后的取景约束与测试结果见 `docs/development/first-session-repair/camera.md:20-34` 和 `docs/development/second-pass/camera.md:1-8`。这说明“镜头跟随”已经存在，但它解决的是可见性，不是地图成长。

### 1.3 关键点位步行时间

下面先给出**无碰撞直线下界**：按移动速度 5.5 世界单位/秒计算，不能当作实际绕障碍路线。移动速度来源：`SalonDemo.Mobile.cs:968-976`。坐标来源分别为 `SalonDemo.cs:160-162`、`SalonGameModel.cs:333-339`、`SalonDemo.Mobile.cs:78-79`、`SalonDemo.cs:600-608`。

- 门口/顾客入口 `(-10.4, -2.7)` → 0 号洗发服务点 `(-6.2, 3.6)`：直线约 **7.57 单位 / 1.38 秒**。
- 0 号洗发服务点 → 1 号理发服务点 `(-1.8, -0.6)`：约 **6.08 单位 / 1.11 秒**。
- 1 号理发服务点 → 后场补给源取货锚点 `(3.15, 0.70)`：约 **5.12 单位 / 0.93 秒**。补给源物体中心是 `(3.15, 1.65)`，取货锚点在其前方 0.95 单位：`SalonDemo.Mobile.cs:78、169-179、201-204`。
- 补给源取货锚点 → 主补给架卸货锚点 `(-1.25, 4.60)`：约 **5.88 单位 / 1.07 秒**。补给架物体中心是 `(-1.25, 5.55)`：`SalonDemo.Mobile.cs:79、184-205`。
- 主补给架卸货锚点 → 收银台附近（收银台中心约 `(7.2, -3.9)`）：约 **11.36 单位 / 2.07 秒**。收银台碰撞/表现中心见 `SalonDemo.cs:600-608`；这是近似目标，不是单独的收银交互锚点。
- 上述指定顺序的直线下界合计约 **35.99 单位 / 6.54 秒**。实际会因墙、家具和避障增加；当前没有一份覆盖“门口→洗发→理发→补给源→货架→收银”的完整实测路径。
- 已有一条真实 Chromium 路线实测可作校准：`source → 货架 → 洗发工位` 购买前 **17.7834 世界单位、7.1954 秒**，购买后 **16.5772 世界单位、6.5744 秒**，少 **1.2062 单位、0.6210 秒**。来源：`docs/development/r1-supply-growth/R1_REPORT.md:44-56`。报告明确说这只是选定循环的功能收益，不能外推成所有路线都变短：`R1_REPORT.md:99-101`。

### 1.4 工位总数与真正可用数

- 模型总共定义 **5 个工位**：0 洗发、1 理发、2 理发、3 烫发、4 洗发。位置和类型见 `unity-hair-salon/Assets/Scripts/SalonGameModel.cs:333-339`。
- 手机开局实际可用 **2 个**：0 号洗发、1 号理发。手机初始化把 2 号理发是否开放交给理发扩建，但把 4 号洗发和 3 号烫发固定传入 `false`：`SalonDemo.cs:240-246`；恢复/刷新路径仍是 `_game.ConfigureWorkstationAvailability(_mobileHaircutExpansionPad.IsUnlocked, false, false)`：`SalonDemo.Mobile.cs:929-939`。
- 理发扩建完成后，手机正式流程可用数变成 **3 个**：0 号洗发、1/2 号理发；扩建只花钱开放 2 号理发并改变右侧地板/通行。扩建状态保存和边界切换见 `SalonDemo.Mobile.cs:770-790`。
- 3 号烫发和 4 号洗发在模型中确实是家具/工位定义，但在当前手机正式流程里没有解锁参数、施工点或存档字段；`ConfigureWorkstationAvailability` 明确分别控制 4 和 3：`SalonGameModel.cs:350-355`。因此结论是：**它们当前属于“摆着但用不了”的家具；不是模型永远不能用，而是按现有手机正式流程没有任何正常路径能解锁，实际效果等同于永远不可用。**
- 这也造成明显的空间/内容落差：房间里有 5 个工位的视觉暗示，但首局玩家只能使用 2 个，最终也只能使用 3 个；未开放的烫发位和第二洗发位会被理解成未完成内容，而不是成长目标。

## 2. 当前扩建到底做了什么

- 当前持久化扩建只有两个施工购买字段：补货架和第二理发工位，成本都为 **180 金币**；存档常量与字段见 `unity-hair-salon/Assets/Scripts/SalonProgressSave.cs:12-30`，范围校验见 `SalonProgressSave.cs:70-94`。
- 自动吹风台的已购状态存在于运行模型，但本次手机两个施工点的保存/恢复路径没有把它做成新的地图区域；用户线索中的“自动吹风 1200”在 `SalonServiceChain.cs:93` 可见，属于设备价格，不等于当前已实现的第三个空间扩建点。
- 补货架施工完成后在现有洗发区附近生成第二个补给架；报告称容量仍为 6，路线收益只在选定循环中测得：`docs/development/r1-supply-growth/R1_REPORT.md:14-22、44-56`。
- 理发施工完成后打开现有房间右侧的一段地板和第二理发工位；代码用 `MobileZoneABounds` / `MobileSalonBounds` 切换地面可走范围，`SalonDemo.Mobile.cs:770-778`。这不是“新房间”，也没有新门、楼层、后场通道或等待区。
- 关闭经营是结果页按钮进入的“闭店经营”弹出面板/状态收尾，不是玩家进入一个可继续探索的扩建管理空间：`unity-hair-salon/Assets/Scripts/SalonDemo.cs:760-790`。当前产品约束仍强调不要把扩建误解为通用区域扩建已经完成：`PROJECT_CONTEXT.md:53-56`。

## 3. 哪些是已批准布局，哪些只是方向

- 已批准基准是 2026-08-31 确认的店铺布局参考图，依据是功能分区、家具成组关系、相邻关系、营业动线和画面密度，不是逐像素施工图：`PROJECT_CONTEXT.md:32`、`PROJECT_CONTEXT.md:72`。
- 2026-09-28 首局修复明确要求保持现有角色、布局和视觉方向，不增加服务、施工点或商业化：`PROJECT_CONTEXT.md:17-18`。因此“房间布局不可擅自重做”目前是硬边界。
- 0003 记录的产品方向包括第二张洗发床、洗发/理发区扩建、补给架、等待区扩建和缩短路线的后场通道：`docs/decisions/0003-hair-salon-hybrid-casual-loop.md:90-100`。
- 但 0003 同时明确：通用区域扩建、场景购买点和连续施工点当时尚未实现，真正落地需要同步模型、存档、场景/Manifest、占地碰撞、导航、工位能力和回归：`docs/decisions/0003-hair-salon-hybrid-casual-loop.md:127-128`。所以等待区、后场通道、门口外摆和“逐段长出地图”目前都是**方向/候选，不是已批准可直接施工的布局变更**。
- 当前最安全的产品表述是：**功能分区关系已批准；把现有分区扩成新房间、增加外摆或开放 3/4 号工位，需要产品负责人单独批准。**

## 4. 竞品对照

以下是网络资料能核实到的机制对照；竞品的“几屏”没有统一官方数字，不能把非官方攻略中的画面感觉写成精确比例。

### Monkey Mart

- 资料显示，玩家在单个 mart 内通过高亮购买点逐步解锁新货架、产品、设备和收银设施；完成当前 mart 的必需摊位/设备后再开下一家 mart。来源：[Burger Bounty 的 Monkey Mart 介绍](https://burgerbounty.io/monkey-mart/)、[AntGames 攻略](https://ant.games/g/monkey-mart)。
- 它的核心是**同一经营场地逐步加走道/摊位，之后再切换到新的 mart 分支**；镜头会短暂聚焦下一个购买位置，给玩家空间成长提示。来源同上。
- “初始地图占几屏、最终占几屏”未找到可靠官方数值，标记为**未核实**。可核实的差距是：本作当前只有一次同房间横向放大，而 Monkey Mart 有连续购买点、多个产品区和多个 mart 分支。

### My Perfect Hotel

- 官方应用商店文案确认：从单人处理接待/房务开始，逐步升级房间和设施、雇员工，再进入更大、不同主题的新酒店；来源：[Google Play 官方页面](https://play.google.com/store/apps/details?id=com.PGS.my.perfect.hotel.game&hl=en)。
- 公开攻略资料描述单个酒店达到等级上限后进入下一酒店；每个酒店有自己的房间、设施和升级，属于**分物业/分场景的多房间成长**。来源：[Simple Game Guide](https://simplegameguide.com/my-perfect-hotel-levels-hotels/)。
- 精确的初始/最终屏数未找到官方口径，标记为**未核实**。对本作的启发是：空间成长不只靠把同一个房间拉宽，还可以通过新房间、新物业和新设施制造明确的阶段感。

### Supermarket Together / 类似超市走格扩建

- 公开资料显示，玩家从经理室的黑板购买 shop space 或 storage space；商店区和仓储区分别扩展，逐步打开新的行/格，后续还能选择不同店铺布局。来源：[Nintendo Smash 扩建说明](https://nintendosmash.com/supermarket-together-how-to-increase-shop-storage-space/)、[Steam 社区更新说明](https://steamcommunity.com/app/2709570/)。
- 这是**在同一经营设施中按格解锁空间**，扩建直接带来摆更多货架、更多产品和更长动线；不是只在闭店面板里加一个数。
- 精确初始/最终屏数未核实；但“分店区/仓储区、按格开放、可选布局”已经明显比本作当前的单次 `15.1→20.7` 单房间放宽更有空间成长层次。

### 胡闹厨房

- 《胡闹厨房》的设计资料明确提到，关卡不会让地图过度铺开、避免镜头完全拉远；布局通常是固定且紧凑的厨房，再用移动台面、传送带、车辆、地震等变化打乱路线和分工。来源：[MCV/Develop post-mortem](https://mcvuk.com/development-news/the-develop-post-mortem-overcooked/)、[Game Developer 设计解析](https://www.gamedeveloper.com/design/game-design-deep-dive-building-truly-cooperative-play-in-i-overcooked-i-)。
- 它不是“经营店铺逐日扩建”的直接竞品：核心是**每关一个紧凑、可读、会变化的固定地图**，镜头优先保持可读性，不为容纳大地图而无限缩远。
- 初始地图/最终地图屏数没有统一数字，标记为**未核实**。对本作的关键启示不是照搬大地图，而是让空间变化产生真实阻碍、路线切换和决策；本作当前固定房间缺少第二阶段的空间变化。

## 5. 三个可选方向

### A：不改房间，只调镜头拉近并跟随

- 玩家感受：店铺会更有纵深、目标更容易和角色同屏，移动更像“我在店里跑”；但玩家走几步就到边界，不能真正解决“内容少/地图长不大”的问题。
- 改动范围：主要是镜头正交尺寸、跟随焦点、UI 安全边距和动态取景；不需要改地板、墙、导航、存档、Manifest 或新资产。
- 已批准布局：**基本不触碰**，可沿用首局镜头修复的授权；需要批准的是“是否接受更近镜头会减少全店总览、可能增加目标切换”的体验取舍。
- 成本：**小**。风险：镜头拉近会让补给源、工位、收银不能同屏，反而增加迷路；它是表现优化，不是空间扩建。

### B：在现有房间外按 0003 逐步开新区域

- 玩家感受：从一个店逐步长出等待区、第二洗发区、后场通道、门口外摆；每次施工都改变路线、拥堵和服务能力，最接近当前产品已写下的“空间触发式扣费扩建”定位。
- 改动范围：新增/重做地板和墙体边界，扩展导航与碰撞，更新镜头取景，增加扩建存档字段和购买点，更新 Manifest 的 footprint/collision/anchors/sorting/shadow，并制作等待区、第二洗发区、后场/外摆资产；需要对应回归和真实画面验收。
- 已批准布局：**触碰批准范围**。需要产品负责人先明确：第一块新增区域究竟是等待区、第二洗发区、后场通道还是外摆；新增区域与现有门、墙、收银、顾客入口如何连接；哪些现有摆着但不可用的工位要开放。
- 成本：**中到大**。风险：导航/碰撞穿模、相机安全区、顾客路径和移动端可读性会同时变复杂；如果只增加空地而不增加服务能力，玩家会觉得是“无意义拉大地图”。

### C：开局更小、最终更大的多房间成长

- 玩家感受：开局压力更集中，随着收入解锁后场、等待区、洗发房或第二房间，最终形成明显的“从小店到完整门店”成长；更接近 Monkey Mart / My Perfect Hotel 的阶段性。
- 改动范围：需要多房间/分区数据、房门或通道、房间级地板/墙/碰撞/导航、镜头切换或更大范围跟随、存档中的房间解锁树、Manifest 和新资产；还要重新设计顾客与员工跨房间路线。
- 已批准布局：**明显触碰**。需要批准最终房间数量、开局删减哪些现有工位/家具、每个房间的解锁顺序，以及是否允许现有 3 号烫发位/4 号洗发位转为后期可用内容。
- 成本：**大**。风险：会改变首局教学、路线压力、镜头规则、顾客寻路和既有截图基准；若没有足够订单/服务内容支撑，地图变大只会放大空跑。

## 6. 建议产品决策顺序

如果当前目标只是缓解“画面看起来小”，先选 A 做低成本镜头实验；如果目标是解决“空间没有成长、扩建没有改变经营结构”，应优先评审 B 的第一块新增区域，而不是直接做 C。C 只有在产品负责人愿意批准新的房间结构、首局重做和更大工程成本时才值得启动。

在任何方向开工前，建议先确认三个问题：第一，3 号烫发位和 4 号洗发位是要删除视觉、作为未来解锁预告，还是在某个批准阶段开放；第二，第一块真正新增空间是什么；第三，扩建必须带来的可感知能力是增加并行服务、减少路线、提高等待容量，还是只做视觉成长。
